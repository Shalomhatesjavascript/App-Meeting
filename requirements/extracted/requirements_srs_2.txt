 
 Software Requirements Specification (SRS) Babcock University Meetup Application Version 1.0 1. Introduction 1.1 Purpose This Software Requirements Specification (SRS) document provides a detailed description of the requirements for the Babcock University Meetup Application. The document is intended for developers, stakeholders, and evaluators to understand the system’s functionality and constraints. 1.2 Scope The application is a web-based, campus-exclusive meetup platform designed for students of Babcock University. Access is restricted to users with valid @student.babcock.edu.ng email addresses. The system enables students to connect based on shared interests and intent while maintaining privacy through progressive profile disclosure. Monetization is implemented using a weekly subscription model. 1.3 Definitions, Acronyms, and Abbreviations SRS – Software Requirements Specification Intent – The purpose of using the application (dating, friendship, networking, study buddy) Match – A mutual expression of interest between two users PWA – Progressive Web Application 1.4 References IEEE 830 Software Requirements Specification Standard 1.5 Overview This document describes the system features, functional and non-functional requirements, constraints, and assumptions. 2. Overall Description 2.1 Product Perspective The system is a standalone web application designed to operate independently while integrating external services such as email verification and payment gateways. 2.2 Product Functions - User registration and authentication - Profile creation and management - Interest-based matching system - Messaging system - Subscription and payment management - Administrative moderation and analytics 2.3 User Classes and Characteristics Students (Free Users): Limited weekly matches and messaging capabilities. Students (Paid Users): Extended access including increased weekly matches and unlimited messaging. Administrators: System moderators with access to analytics and user management tools. 2.4 Operating Environment The application operates on modern web browsers and is containerized for mobile deployment. 2.5 Design and Implementation Constraints User access restricted to Babcock University student emails. Weekly match limits enforced by system rules. 2.6 Assumptions and Dependencies Users possess valid student email addresses and stable internet access. 3. System Features 3.1 User Authentication and Verification Users must register using a valid Babcock University student email. Email verification is mandatory. Optional student ID verification provides a verified badge. 3.2 Profile Management Users can create and edit profiles including name, level, department, gender, intent, bio, and interests. Profile photos remain hidden until a match is established. 3.3 Matching System The system provides swipe-based discovery. Free users are limited to one match per week, while paid users can have up to five matches per week. Matching occurs upon mutual interest. 3.4 Messaging System Messaging is enabled only after a match. Free users have limited messaging, while paid users enjoy unlimited access. 3.5 Subscription and Monetization The system supports weekly subscription payments, unlocking premium features such as additional matches and unrestricted messaging. 3.6 Admin Dashboard Administrators can monitor user activity, manage reports, verify accounts, and suspend or ban users. 4. External Interface Requirements 4.1 User Interfaces Responsive swipe-based user interface optimized for web and mobile. 4.2 Hardware Interfaces No special hardware interfaces required. 4.3 Software Interfaces Integration with email services for verification and payment gateways for subscription processing. 4.4 Communication Interfaces All communications must occur over secure HTTPS connections. 5. Non-Functional Requirements 5.1 Performance Requirements The system should support concurrent users with minimal latency. 5.2 Security Requirements User data must be encrypted. Role-based access control must be enforced. 5.3 Usability Requirements The interface should be intuitive and easy to use for students. 5.4 Reliability and Availability The system should maintain high availability with minimal downtime. 5.5 Maintainability The system should be modular and easy to update. 6. Other Requirements The system should log administrative actions and support analytics for usage trends. 7. Appendices Future enhancements may include event-based matching, voice notes, and AI-assisted recommendations.
